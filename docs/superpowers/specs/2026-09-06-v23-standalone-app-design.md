# Ciao, Web! v23 — Standalone Application Design

Дата: 2026-09-06  
Статус: дизайн согласован по разделам в чате; ожидает финального подтверждения этого файла перед планом реализации  
Ветка: `v23-test`

## 1. Цель

Переписать Ciao, Web! v23 как самостоятельное Telegram Mini App, а не как модификацию v22.5.

Текущая экспериментальная v23 построена поверх HTML v22.5 и legacy DOM. Этот подход прекращается. Новая v23 должна иметь собственный frontend, собственный app shell, собственную навигацию и единый backend-контракт.

Production v22.5 остаётся нетронутой до отдельного подтверждённого релиза v23.

## 2. Что сохраняем из текущего TEST-контура

Сохраняются только инфраструктурные части, уже изолированные от production:

- Cloudflare Worker `ciao-web-v23-test`;
- отдельный Supabase TEST project;
- TEST backend с единственной публичной точкой входа `ciao-v23-api`;
- персональная скрытая TEST-кнопка Telegram;
- TEST whitelist;
- CI/CD для TEST-ветки.

Существующий frontend текущей v23 не является базой нового приложения.

## 3. Жёсткие архитектурные запреты

В новой v23 запрещено:

- загружать, копировать или встраивать `v22-5.html`;
- использовать `legacy-surface-adapter`;
- инжектить новый UI в DOM старого приложения;
- иметь два конкурирующих router/state/DOM owner;
- проксировать запросы через старую цепочку `v6 -> v5 -> v4 -> core`;
- держать отдельную frontend-логику для Серии А и еврокубков;
- использовать production Supabase в TEST;
- переносить TEST-базу поверх production;
- выполнять destructive migrations production-базы до подтверждённой стабильности v23.

## 4. Целевая архитектура

### TEST

`Telegram -> ciao-web-v23-test -> ciao-v23-api -> TEST Supabase`

### Production после отдельного релиза

`Telegram -> production v23 frontend -> production ciao-v23-api -> существующая production Supabase`

Frontend и backend используют одинаковый контракт в TEST и production. Различаются только environment/configuration и база данных.

## 5. Frontend

Новый frontend создаётся с нуля и имеет:

- собственный `index.html`;
- один app shell;
- один router;
- одно хранилище состояния;
- один Telegram init;
- один API client;
- один live/polling controller;
- независимые экраны;
- переиспользуемые UI-компоненты.

Основные общие компоненты:

- Bottom Navigation;
- Match Card;
- Team Badge;
- Tournament Card;
- Profile Summary;
- Loading Skeleton;
- Inline Error State;
- Empty State;
- Match Center header/tabs.

Каждый крупный модуль имеет одну понятную ответственность и не зависит от DOM другого экрана.

## 6. Визуальное направление

Используется фирменный тёмно-синий стиль Ciao, Web!, но интерфейс рисуется заново.

Принципы:

- глубокий тёмно-синий фон;
- карточки на 1–2 тона светлее основного фона;
- белый основной текст;
- синие/голубые активные состояния;
- мягкие скругления;
- минимальные бордеры;
- минимум визуального шума;
- крупные ключевые числа и действия;
- единая система размеров, отступов, карточек и состояний.

Новая v23 не обязана визуально копировать карточки v22.5.

## 7. Основная навигация

Нижнее меню содержит ровно пять разделов:

1. Главная
2. Прогнозы
3. Рейтинг
4. Матчи
5. Таблицы

Текст подписей всегда видим.

Пример route-модели:

- `/home`
- `/predictions`
- `/predictions/mine`
- `/ranking/all`
- `/ranking/italy`
- `/ranking/europe`
- `/matches/serie-a`
- `/matches/coppa-italia`
- `/matches/ucl`
- `/matches/uel`
- `/matches/uecl`
- `/match/:competition/:matchId/:section`
- `/tables/serie-a`
- `/tables/ucl`
- `/tables/uel`
- `/tables/uecl`

Router хранит history Mini App. Back восстанавливает предыдущий экран, subview, tournament, filters и scroll.

Telegram Back Button и browser/system Back используют одну и ту же навигационную модель.

Каждый основной раздел запоминает своё последнее состояние.

## 8. Главная

Главная — компактный обзор, а не копия всех разделов.

Содержит:

- шапку Ciao, Web!;
- аватар пользователя;
- компактный профиль;
- очки;
- место в рейтинге;
- точные счета;
- любимый клуб;
- ближайший матч любимого клуба;
- блок «Кальчо сегодня»;
- live-матчи, если они идут.

Прогнозы на Главной не показываются.

### 8.1. Любимый клуб

Пользователь выбирает один любимый итальянский клуб.

Карточка любимого клуба показывает ближайший матч среди всех поддерживаемых соревнований. Вся карточка матча открывает Match Center.

Если клуб не выбран, показывается явное действие выбора клуба.

### 8.2. Кальчо сегодня

Показываются матчи текущего локального дня пользователя, в которых участвует клуб Серии А, включая допустимые матчи Кубка Италии и еврокубков.

Если матчей нет, точный текст:

`Кальчо сегодня нет :(`

Live-матчи сортируются выше обычных сегодняшних матчей.

## 9. Поддерживаемые соревнования

Внутренние стабильные ID:

- `serie_a`
- `coppa_italia`
- `ucl`
- `uel`
- `uecl`

Пользовательские названия только на русском:

- Серия А
- Кубок Италии
- Лига чемпионов
- Лига Европы
- Лига конференций

Технические ID никогда не отображаются в UI.

## 10. Ключевое правило еврокубков

Для Лиги чемпионов, Лиги Европы и Лиги конференций приложение учитывает только матчи, где хотя бы один участник — итальянский клуб.

Это правило применяется на backend-уровне и обязательно действует для:

- Матчей;
- Прогнозов;
- Моих прогнозов;
- Кальчо сегодня;
- ближайшего матча любимого клуба;
- Match Center;
- live-обновлений;
- рейтинга «Еврокубки»;
- общего рейтинга в еврокубковой части;
- матчевых уведомлений.

Квалификационные и предварительные раунды еврокубков исключаются полностью.

Frontend не определяет самостоятельно, является ли матч «итальянским». Backend отдаёт только допустимые матчевые сущности.

Итальянская принадлежность определяется по стабильному `team_id` и нормализованному клубному справочнику/стране, а не по названию строки.

API отклоняет попытку сохранить прогноз на недопустимый еврокубковый матч даже при ручном запросе.

### Исключение для раздела «Таблицы»

Правило «только матчи итальянских клубов» не урезает общие турнирные таблицы.

В разделах:

- Таблицы -> Лига чемпионов;
- Таблицы -> Лига Европы;
- Таблицы -> Лига конференций

отображается полная актуальная турнирная таблица со всеми командами соответствующего соревнования. Все названия команд при этом локализуются на русский язык.

Таким образом, фильтр по итальянским клубам относится к матчевым сущностям, прогнозам, live, рейтингу и уведомлениям, но не к строкам общей турнирной таблицы.

## 11. Прогнозы

Раздел содержит две вкладки:

- Прогнозы
- Мои прогнозы

Фильтр соревнований:

- Все
- Серия А
- Кубок Италии
- Лига чемпионов
- Лига Европы
- Лига конференций

### 11.1. Прогнозы

Показываются только матчи, на которые прогноз ещё открыт.

Правила:

- дедлайн: за 15 минут до kickoff;
- до дедлайна прогноз можно создавать и изменять;
- после дедлайна изменение запрещено;
- сохранённый прогноз немедленно отображается в карточке;
- сохранение подтверждается inline-состоянием, без системного popup;
- еврокубки содержат только допустимые матчи итальянских клубов;
- квалификации отсутствуют.

### 11.2. Мои прогнозы

Для каждого прогноза показываются:

- турнир;
- команды;
- локальное время;
- поставленный счёт;
- фактический счёт после завершения;
- начисленные очки;
- статус матча.

До дедлайна пользователь может вернуться к прогнозу и изменить его.

## 12. Система начисления очков

Единая система для всех поддерживаемых турниров:

- 5 — точный счёт;
- 3 — точная разница мячей при правильном исходе;
- 2 — правильный исход;
- 0 — промах.

Дедлайн всегда равен `kickoff UTC - 15 минут`.

Frontend не пересчитывает очки и не определяет дедлайн самостоятельно как источник истины.

## 13. Рейтинг

Три scope:

- Все
- Италия
- Еврокубки

Состав:

- `Все` = Серия А + Кубок Италии + допустимые матчи UCL/UEL/UECL;
- `Италия` = Серия А + Кубок Италии;
- `Еврокубки` = только допустимые матчи итальянских клубов в UCL/UEL/UECL.

Backend возвращает уже рассчитанную таблицу рейтинга для выбранного scope.

## 14. Матчи

Стартовый экран содержит пять крупных карточек турниров:

- Серия А
- Кубок Италии
- Лига чемпионов
- Лига Европы
- Лига конференций

### 14.1. Серия А

Матчи группируются по турам и статусам.

### 14.2. Кубок Италии

Отображение начинается с 1/8 финала. Более ранние стадии не показываются.

### 14.3. Еврокубки

Показываются только допустимые матчи итальянских клубов. Квалификации отсутствуют.

Вся карточка матча открывает единый Match Center.

## 15. Match Center

Match Center — отдельный полноценный экран, общий для всех соревнований.

Вкладок ровно пять:

1. Обзор
2. Статистика
3. События
4. Составы
5. Игроки

### 15.1. Обзор

Может содержать:

- статус;
- дату и локальное время;
- стадион;
- тур/стадию;
- текущий или итоговый счёт.

### 15.2. Статистика

Отображаются только реально полученные показатели. Отсутствующее значение не подменяется нулём.

### 15.3. События

Поддерживаются доступные у провайдера:

- голы;
- автоголы;
- пенальти;
- жёлтые/красные карточки;
- замены;
- VAR.

### 15.4. Составы

- стартовые 11;
- схема;
- запасные;
- тренер, если доступен.

### 15.5. Игроки

Показывается статистика игроков конкретного матча, если она есть у провайдера.

Match Center не имеет отдельной реализации для Серии А.

## 16. Таблицы

Раздел содержит:

- Серия А
- Лига чемпионов
- Лига Европы
- Лига конференций

Кубка Италии в разделе «Таблицы» нет.

Для Лиги чемпионов, Лиги Европы и Лиги конференций отображается полная турнирная таблица со всеми клубами, а не только с итальянскими участниками.

Все названия клубов, турниров, стадий и подписи колонок отображаются на русском языке.

## 17. Единая модель матча

Frontend должен работать с одной нормализованной сущностью матча независимо от турнира.

Минимальный контракт включает:

- `competition`;
- `provider_match_id`;
- `season`;
- `stage`;
- `round`;
- `kickoff_at`;
- `status`;
- `home_team`;
- `away_team`;
- `score`;
- `is_italian_relevant`;
- `is_qualification`.

Serie A и внешние турниры не должны требовать разных UI-контрактов.

## 18. Единая модель прогноза

Целевая логическая модель:

- `user_id`;
- `match_id`;
- `home_score`;
- `away_score`;
- `points`;
- `created_at`;
- `updated_at`;
- `locked_at`.

Допускается поэтапная миграция существующих production-таблиц, но frontend не должен знать, в какой физической таблице хранится прогноз.

## 19. Источник футбольных данных

BSD остаётся внешним провайдером, но его сырой ответ никогда не используется UI напрямую.

Поток:

`BSD -> normalization/filtering/localization metadata -> ciao-v23-api -> frontend`

Backend отвечает за:

- нормализацию соревнований;
- определение итальянских клубов;
- исключение квалификаций;
- нормализацию статусов;
- дедлайн;
- начисление очков;
- live-состояния;
- защиту допустимости прогнозов.

## 20. Русская локализация

Интерфейс v23 — русскоязычный.

Все отображаемые названия клубов должны иметь каноническое русское имя по стабильному `team_id`.

Примеры:

- Inter -> Интер;
- Juventus -> Ювентус;
- Bayern München -> Бавария;
- Paris Saint-Germain -> ПСЖ;
- Manchester City -> Манчестер Сити.

Названия турниров и стадий локализуются централизованно.

Примеры стадий:

- `Round of 16` -> `1/8 финала`;
- `Quarter-finals` -> `1/4 финала`;
- `Semi-finals` -> `1/2 финала`;
- `Final` -> `Финал`;
- `League phase` -> `Общий этап`.

Технические английские значения не должны просачиваться в UI.

## 21. Склонения и русский язык

В v23 используется единый localization/grammar layer.

Он отвечает за:

- 1 очко / 2 очка / 5 очков;
- 1 матч / 3 матча / 10 матчей;
- 1 прогноз / 2 прогноза / 7 прогнозов;
- 1 гол / 4 гола / 11 голов;
- правильные формы названий турниров: `в Серии А`, `в Кубке Италии`, `в Лиге чемпионов`;
- даты: `21 сентября`;
- корректные падежные формы клубов там, где они реально нужны.

Для клубов не используется наивное автоматическое склонение строки. Нужные формы могут храниться в локализационном справочнике по `team_id`; для неоднозначных случаев UI формулируется так, чтобы не требовать спорного склонения.

Запрещены ручные конструкции вида `число + "очков"` без grammar formatter.

Автотесты обязаны проверять минимум значения:

`1 / 2 / 5 / 11 / 21 / 22 / 25`.

## 22. Локальное время пользователя

Все kickoff timestamps хранятся и передаются как абсолютное время/UTC.

Frontend показывает время в локальном часовом поясе устройства пользователя.

Формат — русский (`ru-RU`), например:

- `Сегодня · 21:45`;
- `Завтра · 19:30`;
- `12 сентября · 21:45`.

Смена часового пояса устройства меняет только отображение.

Момент дедлайна не зависит от локализации и всегда рассчитывается относительно абсолютного kickoff.

## 23. Профиль пользователя

Telegram является источником изменяемых полей профиля:

- first name;
- last name;
- username;
- avatar, если доступен.

При входе эти поля синхронизируются.

Telegram ID остаётся стабильной пользовательской идентичностью и никогда не заменяется из-за изменения имени или username.

## 24. Любимый клуб

Пользователь выбирает один любимый итальянский клуб.

Выбор сохраняется в базе и используется для:

- Главной;
- ближайшего матча;
- Кальчо сегодня;
- быстрых переходов;
- уведомлений, где это применимо.

Поиск клуба работает по русскому названию.

## 25. Настройки

Компактный экран настроек содержит:

### Уведомления

- дедлайн прогнозов;
- составы;
- начало матча;
- результат матча.

### Приложение

- любимый клуб;
- локальное время определяется автоматически;
- язык первой версии — русский.

Ручной timezone override не входит в первую версию.

## 26. Уведомления

Уведомления формируются backend-логикой и не зависят от того, открыт ли Mini App.

Они используют русский localization/grammar layer.

Еврокубковые матчевые уведомления разрешены только для матчей с итальянскими клубами.

Примеры типов:

- напоминание о дедлайне;
- опубликованный состав;
- начало матча;
- итоговый результат.

## 27. Live и polling

В приложении один владелец polling.

Правила:

- live-счёт и минута обновляются без перезагрузки всего приложения;
- Match Center может обновляться чаще, когда открыт live-матч;
- ненужные запросы прекращаются после ухода с live-экрана;
- нет независимых таймеров в разных компонентах;
- временная ошибка обновления не уничтожает последний корректный snapshot.

## 28. Ошибки и last-good-data

Каждый крупный блок изолирован от других.

Если один запрос падает:

- навигация продолжает работать;
- другие блоки не ломаются;
- последний успешный результат остаётся видимым;
- появляется локальное состояние `Не удалось обновить`;
- пользователь может повторить запрос.

Полный offline mode в первую версию не входит.

Используется session-level last-good-data cache.

## 29. Производительность

Приложение загружает только данные текущего экрана.

Примеры:

- Главная не загружает полные составы всех матчей;
- Match Center не загружает данные вкладки `Игроки`, пока пользователь её не открыл;
- live polling активен только там, где он нужен;
- одна сущность не запрашивается несколькими независимыми владельцами без необходимости.

## 30. Production-база и миграции

Production Supabase не пересоздаётся и не заменяется TEST-базой.

При релизе v23 переносится код и совместимые изменения схемы.

Существующие production-данные должны сохраниться:

- пользователи;
- Telegram ID;
- прогнозы;
- начисленные очки;
- пользовательские настройки;
- история.

Правила migrations:

- новые таблицы можно добавлять;
- новые столбцы можно добавлять;
- индексы и ограничения можно добавлять после проверки совместимости;
- существующие данные нельзя обнулять;
- старые таблицы/поля не удаляются до подтверждённой стабильности v23;
- миграции не должны намеренно ломать rollback на v22.5 в период перехода.

TEST-данные никогда не копируются в production.

## 31. Release и rollback

До релиза production работает v22.5.

Релиз v23 разрешён только после:

1. зелёных автоматических тестов;
2. успешной сборки standalone frontend;
3. проверки TEST isolation;
4. реального smoke-test через скрытую Telegram TEST-кнопку;
5. явного подтверждения владельца проекта.

Зелёный CI сам по себе не является разрешением на production deploy.

До подтверждения стабильности v23 сохраняется возможность вернуть frontend v22.5 без потери production-базы.

## 32. Обязательные автоматические проверки

Перед production должны автоматически подтверждаться как минимум следующие условия:

- frontend не импортирует legacy v22.5;
- build не загружает `v22-5.html`;
- нет `legacy-surface-adapter`;
- приложение запускается с собственного пустого app shell/index;
- существует один router owner;
- существует один live/polling owner;
- все пять основных разделов доступны;
- Back восстанавливает экран/subview/tournament/filters/scroll;
- Telegram Back и browser/system Back используют одну модель;
- Match Center имеет ровно пять утверждённых вкладок;
- Кубок Италии в Матчах начинается с 1/8 финала;
- Кубка Италии нет в Таблицах;
- UCL/UEL/UECL матчевые endpoint'ы не возвращают матч без итальянского клуба;
- UCL/UEL/UECL не возвращают квалификации;
- попытка сохранить прогноз на запрещённый еврокубковый матч отклоняется;
- `Рейтинг -> Еврокубки` не учитывает запрещённые матчи;
- еврокубковые турнирные таблицы при этом остаются полными и включают все команды;
- названия турниров и клубов отображаются на русском;
- grammar tests проходят для `1/2/5/11/21/22/25`;
- kickoff отображается в локальном timezone пользователя;
- дедлайн остаётся `kickoff - 15 минут` независимо от timezone;
- временная ошибка API не уничтожает last-good-data;
- профиль синхронизирует Telegram name/username без изменения Telegram ID;
- TEST frontend не содержит production Supabase references;
- production migration path не предполагает замену базы TEST-базой.

## 33. Критерии готовности к реальному Telegram smoke-test

TEST-сборка готова к пользовательской проверке только когда:

- она является standalone frontend, а не оболочкой v22.5;
- основные маршруты работают;
- API-контракт стабилен;
- отображается русский UI;
- еврокубковая фильтрация работает на backend;
- локальное время работает;
- нет пустых экранов при Back;
- ошибки не разрушают app shell.

## 34. Критерии готовности к production

Production promotion возможен только если:

- все критерии smoke-test выполнены;
- автоматические проверки зелёные;
- реальная Telegram-проверка пройдена;
- migration plan для существующей production-базы отдельно проверен;
- rollback v22.5 остаётся доступен;
- владелец проекта явно разрешил production-релиз.

## 35. Итоговый принцип

v23 — новое самостоятельное приложение.

Мы сохраняем существующую production-базу и пользовательские данные, но не сохраняем legacy frontend-архитектуру v22.5.

Основное правило разработки: один источник истины для данных, одна навигация, один app shell, один backend-контракт и никакого нового интерфейса поверх старого DOM.
